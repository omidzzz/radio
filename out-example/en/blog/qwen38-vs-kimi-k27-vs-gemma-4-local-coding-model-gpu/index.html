#Qwen3.8 vs Kimi K2.7 vs Gemma 4: Which Local Coding Model Fits Your GPU?

Every few weeks a new open-weight coding model arrives with a benchmark table that makes it look like the obvious choice. Then you try to run it and discover the real constraint was never the leaderboard. It was the memory on the card sitting in your machine. Qwen3.8-27B, Kimi K2.7 Code, and Gemma 4 are three of the most discussed open-weight options in 2026, and they occupy completely different hardware tiers. One of them fits a single consumer GPU. One of them does not fit anything you own. One of them scales from a phone to a workstation.

This is a hardware-first comparison rather than a benchmark-first one. Benchmark scores matter, but they are almost all vendor-reported, measured on harnesses that differ between vendors, and they tell you nothing about whether the model will actually load on your machine with a usable context window. The order of operations that saves people the most time is simple: work out your memory budget, eliminate everything that cannot fit, and only then argue about which of the survivors is smarter.

#1. The Question Behind the Question

When someone asks which local coding model is best, they are usually asking three separate questions at once, and the answers point in different directions.

If you liked this sectionHow to Fix Cline's Most Common Errors (And Why They Happen)

The first question is which model produces the best code. The second is which model will run on the hardware they already own, at a speed that does not break their concentration. The third, which people rarely say out loud, is which model will still behave sensibly when it is driven by an agent that makes dozens of tool calls in a row rather than answering a single prompt. A model can win the first question and lose the other two badly enough that it is useless to you.

Qwen3.8-27B, Kimi K2.7 Code, and Gemma 4 are useful precisely because they separate cleanly along these lines. Qwen3.8-27B is the current answer for someone with one good consumer GPU who wants agentic coding behaviour. Kimi K2.7 Code is genuinely open-weight and genuinely out of reach for local hardware, which makes it an API decision dressed as a self-hosting decision. Gemma 4 is a family rather than a model, and its value is that it scales down further than either of the others without falling off a cliff.

Treating them as three entries on the same list is the mistake. They are three different answers to three different constraints. The rest of this comparison walks through the memory math first, then each model in turn, then a tier-by-tier recommendation you can act on.

#2. The Memory Math to Do Before You Download Anything

Almost every disappointing local model experience traces back to one of three arithmetic mistakes: forgetting quantization, forgetting the KV cache, or forgetting that a mixture-of-experts model still has to hold all of its weights in memory.

//The weight footprint rule of thumb

A workable planning estimate is roughly 0.6GB of memory per billion parameters at Q4_K_M quantization. A 12B model lands near 7-8GB, a 27B model near 16-18GB, a 31B model near 19-20GB. These are estimates derived from parameter count rather than measured downloads, so treat them as planning figures and verify the actual file size in the model library before you commit. Full-precision weights are a completely different conversation: Qwen3.8-27B in BF16 requires roughly 55.6GB, which is why nobody runs it that way on a desktop.

//The KV cache is not optional

Weights are the floor, not the total. The KV cache sits on top and scales with both context length and concurrency. A 27B model serving long-context requests to multiple users can double its memory footprint. This is the single most common reason a model that supposedly fits a 24GB card starts spilling to system RAM the moment someone points an agent at a large repository. Budget 20-30% headroom on top of the weight figure for context, and more if you plan to run long sessions or serve more than one request at a time.

//Mixture-of-experts does not mean lightweight

MoE architectures reduce compute per token by routing each token to a small subset of experts. They do not reduce the memory needed to store the model. Kimi K2.7 Code activates 32 billion parameters out of roughly one trillion total, which is about 3% of the model, and that is the entire reason a trillion-parameter model can be served at competitive prices. It is not a reason it will run on your GPU. All of those weights still need to be resident somewhere. This distinction catches people out constantly, because the marketing language around MoE emphasises the active parameter count.

  • Estimate weights: parameter count multiplied by roughly 0.6GB at Q4_K_M.
  • Add 20-30% headroom for KV cache, more for long context or concurrent requests.
  • Check whether the model is dense or MoE - and remember MoE saves compute, not memory.
  • Confirm the actual package size in the model library rather than trusting the estimate.
  • On Apple Silicon, count unified memory the same way, and leave room for the operating system.

Applied to consumer hardware, this produces a fairly clean set of tiers. An 8GB card handles 7-12B models. A 16GB card handles the 14-20B class comfortably. A 24GB card is where 27-31B models become realistic at 4-bit. Beyond roughly 32GB you are into multi-GPU rigs or high-memory Mac Studios, and beyond that you are building a small server rather than a workstation.

#3. Qwen3.8-27B: The Default Answer for a 24GB GPU

If you have one good consumer GPU and you want agentic coding behaviour rather than autocomplete, Qwen3.8-27B is currently the model to beat.

//What it actually is

Alibaba announced Qwen3.8-27B on 3 August 2026 alongside the much larger Qwen3.8-Max, and released the open weights around 13-14 August under Apache 2.0. The checkpoint is dense - roughly 27.78 billion parameters - which means the full parameter count sits in VRAM and the memory math above applies directly with no MoE asterisk. It runs 64 layers with a hybrid Gated DeltaNet and Gated Attention design and a 5120 hidden dimension, carries a native 262,144-token context window extensible toward one million tokens with YaRN, and is natively multimodal: it accepts text, image, and video input.

Full BF16 weights need roughly 55.6GB. At 4-bit it runs on a single 24GB GPU, and the Ollama library lists packages around 18GB for both the standard and MLX variants. That 18GB figure is the practical number to plan around. It leaves real headroom on a 24GB card and makes the model uncomfortable but not impossible on 20GB.

//What the benchmarks claim

Qwen's launch card reports 61.7 on SWE-bench Pro, 73.0 on Terminal-Bench 2.1 with the Terminus harness, 90.3 on LiveCodeBench v6, 89.2 on GPQA Diamond, 79.5 on IFBench, and 84.3 on OSWorld-Verified. The generational comparison is the more interesting part: against Qwen3.6-27B, SWE-bench Pro moves from 53.5 to 61.7, Terminal-Bench from 63.4 to 73.0, QwenSWEBench from 49.3 to 79.0, and DeepSWE 1.1 from 13.3 to 42.2. Outside code, CoWorkBench rises from 61.0 to 70.7 and Agents' Last Exam pass@1 doubles from 10.6 to 20.4.

The shape of those gains is the signal. The published configuration is architecturally identical to Qwen3.6-27B - same layer layout - so the story is new weights and new post-training rather than a new architecture. Qwen trained this checkpoint to keep working through an environment across many steps, not to produce a better first response. For anyone using a local model inside an agent loop, that is the property that matters most.

//The caveats that come with those numbers

Every figure above is vendor-run. Qwen's own card is unusually transparent about conditions, which is to its credit and also a reminder of how much conditions matter. SWE-bench Pro was evaluated on a Claude Code harness at temperature 1.0, top-p 0.95, with a 256K context window. QwenSWEBench is an average of three runs with an eight-hour timeout and a 32,768 generated-token cap. Several of the headline benchmarks - QwenSWEBench, CoWorkBench, RecreationBench - are designed in-house, so their tasks and graders do not have the external auditability of a mature public suite.

One comparison in particular deserves care. Qwen reran several rival models on a corrected task set using Claude Code, but imported Claude Opus 4.6 Max's official SWE-bench Pro score rather than rerunning it. So the frequently repeated claim that a 27B open model beats Opus on agentic coding rests on figures from two different harnesses. The gap may well be real. It is not a controlled result, and a public task set does not make a vendor-run number independent.

//Who should run it

Anyone with 24GB of VRAM or 24GB-plus of unified memory on Apple Silicon who wants a local model that can drive an agent through multi-step work. Thinking is enabled by default, and the model exposes controls including reasoning_effort, the ability to disable thinking, and preserve_thinking for whether prior reasoning blocks survive into later turns. Those controls change latency, memory use, and task quality, so they are worth tuning deliberately rather than leaving at defaults.

#4. Kimi K2.7 Code: Open Weights You Probably Cannot Run

Moonshot AI's coding model is genuinely open-weight, genuinely strong, and genuinely not a local model for anyone reading this on a laptop.

//The architecture, and why the headline number misleads

Kimi K2.7 Code was released on 12 June 2026 as a coding-specialised successor to Kimi K2.6. It is a mixture-of-experts model with one trillion total parameters and 32 billion activated per token, routed across 384 experts with eight selected per token plus one shared expert. It runs 61 layers including one dense layer, uses Multi-head Latent Attention and SwiGLU activations, ships with native INT4 quantization, and carries a 256K-token context window. The weights are on Hugging Face under a Modified MIT license, and Moonshot documents deployment via vLLM, SGLang, and KTransformers.

The trillion-parameter headline is the part that gets repeated and the 32B active figure is the part that gets misread. Activating 3% of the model per token is why it can be served at roughly $4.00 per million output tokens instead of at prices a model that size would historically demand. It does not shrink the storage requirement. A representative self-hosting recipe uses a tensor-parallel size of eight, which is to say eight GPUs, with chunked prefill enabled to stop memory spiking during large prefills at 256K context. That is a server deployment, not a desktop one.

//The design choice that defines it

Thinking mode cannot be turned off. That is Moonshot's explicit bet that always-reasoning produces a more reliable coding agent, and it is a real trade-off rather than a marketing line. You cannot dial it down for a trivial task to save tokens or latency. Moonshot's counterweight is efficiency: the model reportedly uses roughly 30% fewer reasoning tokens per coding task than K2.6, which reduces output token count and improves effective throughput per request. There are also two API flavours sharing the same weights - the standard model and a highspeed variant tuned for roughly 180 tokens per second, up to 260 on short contexts, at exactly double the price on every tier.

//Read the benchmark claims carefully

Moonshot reports a 21.8% improvement on Kimi Code Bench v2 over K2.6. That benchmark is first-party, and the release-day table is the only detailed source available from the vendor. Some practitioners have already said the published numbers do not match what they see in real repositories. This is not a reason to dismiss the model - it is a reason to treat the numbers as company-reported positioning rather than an independent leaderboard result, which is exactly how the more careful coverage has labelled them.

One detail worth flagging: sources disagree about whether the MoonViT vision encoder carried over from K2.6. Some deployment write-ups state the vision encoder is absent in the coding-focused K2.7, while the model card summaries and several API listings describe it as natively multimodal with image input. If multimodality matters to your use case, verify against the current model card rather than trusting any secondary source, including this one.

//So what is it actually for?

Kimi K2.7 Code belongs in this comparison as a boundary marker. It is what the open-weight frontier looks like in 2026: genuinely downloadable, genuinely permissively licensed, and genuinely requiring hardware that costs more than a car. For most teams the honest path is the API, and the open weights function as an escape hatch - the guarantee that you could self-host if the vendor relationship went wrong, and leverage in any conversation about pricing or data handling. That guarantee has real value. It is just not the same thing as a local model.

It is also worth noting that Moonshot has since shipped Kimi K3, a 2.8 trillion parameter open-weight multimodal reasoning model using KDA and Attention Residuals, which moved the scale frontier again. The frontier open-weight tier - Kimi K3, GLM-5.2, DeepSeek-V4-Pro - remains out of reach on a single 128GB machine, and pretending otherwise is how people end up with a model paging to SSD at two tokens per second.

#5. Gemma 4: The Family That Scales Down Without Falling Over

Gemma 4 is the only entry here that is a family rather than a model, and that is the entire point of it.

//Five sizes, one architecture story

Google DeepMind released Gemma 4 on 2 April 2026 under Apache 2.0, initially in E2B, E4B, 26B A4B, and 31B variants, then added Gemma 4 12B Unified on 3 June 2026. E2B and E4B run roughly 2.3 and 4.5 billion effective parameters and target phones and edge devices. The 26B A4B is a mixture-of-experts model activating 3.8 billion of 25.2 billion parameters and fits a single RTX 3090 or 4090. The 31B is dense and targets workstations. Context runs to 128K on the edge models and 256K on the three larger ones.

The 12B Unified variant is the interesting addition for local users. It carries 11.95 billion parameters across 48 layers with 1024-token sliding window attention, a 262K vocabulary, and native support for text, image, and audio input. Its Ollama package is around 7.6GB, which puts it squarely in 8GB-card territory. Every Gemma 4 size takes image input; E2B, E4B, and 12B also take audio.

//The speculative decoding advantage

Google shipped Gemma 4 MTP drafters on 16 April 2026 - dedicated draft models for speculative decoding across all five sizes. The claim is up to 3x faster inference at identical quality. This is an underrated practical advantage for local use, because the thing that makes a local model feel unusable is rarely quality and usually latency. If you are running llama.cpp, using the MTP drafters is one of the few free speed wins available.

//Where it stands on capability

The 31B dense model reports 85.2% on MMLU Pro, 89.2% on AIME 2026, 84.3% on GPQA Diamond, 80.0% on LiveCodeBench, and a Codeforces Elo around 2150. On Arena AI's open-source text leaderboard it has held roughly 1452 Elo, with the 26B A4B at about 1441 - competitive with models many times its size. The generational jump from Gemma 3 is dramatic on math and coding in particular.

The honest framing is that Gemma 4 is a very good general model with solid coding ability, not a coding specialist. If your work is heavily agentic software engineering, Qwen3.8-27B's training focus shows. If your work mixes code with document understanding, image input, audio, or multilingual requirements - Gemma 4 supports 35-plus languages out of the box with pre-training across 140-plus - the family is a stronger all-round fit. And since 1 September 2026, Gemma 4 ships inside Android Studio Quail 4 as a fully local coding model, which makes it the path of least resistance for Android work specifically.

One maintenance note that catches people: if you pulled Gemma 4 weights before roughly mid-July 2026, re-pull them. Early checkpoints were revised, and a stale local copy will quietly underperform the numbers you read about.

#6. The Tier-by-Tier Recommendation

Find your memory budget, then read only your row. Everything above it is aspiration and everything below it is a compromise you do not need to make.

//8GB VRAM

You are in the 7-12B class. Gemma 4 12B Unified at roughly 7.6GB is the strongest general-purpose pull at this tier, and it brings multimodality with it. If you want something dedicated to code, JetBrains' Mellum2-12B reports 69.9 on LiveCodeBench and is the strongest coding-specific option that fits. Do not attempt a 27B model here. Quantizing further to force it in trades away exactly the reasoning reliability you wanted the bigger model for.

//12-16GB VRAM

The 14-20B class is comfortable. Gemma 4 12B Unified now has real context headroom rather than fitting on a technicality, and mid-size options such as mistral-small3.2:24b at around 15GB become viable if you keep context modest. This tier is where you should think hardest about context length, because it is the variable that decides whether you fit or spill.

//24GB VRAM

This is the Qwen3.8-27B tier, and it is the clearest recommendation in this entire comparison. Roughly 18GB for weights leaves genuine headroom for context. Gemma 4 31B is the alternative if you want the stronger general model, and Gemma 4 26B A4B is worth testing precisely because it lands within a few points of the 31B on several benchmarks while activating only 3.8 billion parameters, which means noticeably faster generation.

//32GB and above, and Apple Silicon

Above 32GB you gain the ability to run 27-31B models at higher precision, or to run a 27B model with a genuinely long context rather than a nominal one. On Apple Silicon, unified memory counts the same way, with the caveat that the OS and everything else you have open take their share. A 32GB Mac runs a 27B class model well. A 64GB or 128GB Mac Studio opens up more, but the frontier open-weight models - Kimi K3, GLM-5.2, DeepSeek-V4-Pro - stay out of reach even at 128GB.

//Multi-GPU servers

This is where Kimi K2.7 Code becomes a real option rather than a thought experiment, with a tensor-parallel size of eight as a representative configuration. If you are provisioning this, you already know it. For everyone else, the API is the honest answer.

  • 8GB: Gemma 4 12B Unified for general work, Mellum2-12B for code-only.
  • 16GB: Gemma 4 12B with comfortable context, or a 20B-class model with restraint.
  • 24GB: Qwen3.8-27B for agentic coding; Gemma 4 31B or 26B A4B for general strength.
  • 32GB+: the same models with real context, or higher precision quantization.
  • Multi-GPU: Kimi K2.7 Code and the rest of the frontier open-weight tier.

#7. How to Read Vendor Benchmarks Without Being Fooled

Every number in this article, and in almost every comparison you will read, was produced by the company that made the model. That does not make the numbers useless. It makes them evidence with a known bias.

Four habits will protect you from most of the damage. First, attribute every figure to whoever ran it. A public task set does not make a vendor-run result independent; the harness, the temperature, the context window, and the timeout all move the score. Second, separate in-house benchmarks from public ones. When a vendor designs the benchmark, the tasks, and the grader, the number tells you what the vendor optimised for, which is worth knowing but is not a capability measurement.

Third, record which judge model was used. Several benchmarks are scored by another language model, and a score judged by GPT-4o is not directly comparable to one judged by a different model or by execution. Fourth, never merge rows from different conditions into an average. A code-interpreter-enabled result and a no-code-interpreter result are different experiments, and a vision benchmark judged by one model snapshot is not the same measurement as one judged by another.

Applied to these three models, the practical conclusion is that the ordering is probably roughly right and the margins are probably wrong. Qwen3.8-27B is very likely better at agentic coding than its predecessor by a meaningful amount. Whether it genuinely beats a frontier closed model on SWE-bench Pro is not established by an imported score from a different harness. Kimi K2.7 Code is very likely a strong coding model and its self-reported 21.8% gain over K2.6 is very likely directionally real. Gemma 4's Arena Elo figures are the closest thing here to an independent signal, because Arena ratings come from human preference rather than from the vendor.

  • Attribute every number to the party that ran the evaluation.
  • Separate in-house benchmarks from established public suites.
  • Note the harness, temperature, context window, and token caps.
  • Record which model, if any, acted as judge.
  • Never average across different experimental conditions.

#8. Context Windows Are a Memory Decision, Not a Feature

A 262K context window on the model card and a 262K context window on your machine are different things, and the gap between them is measured in gigabytes.

All three models advertise long context: 262,144 tokens native for Qwen3.8-27B with YaRN extension toward a million, 256K for Kimi K2.7 Code, and 256K for the larger Gemma 4 variants. None of those figures are free. The KV cache grows with the context you actually use, and it comes out of the same memory pool as the weights. A model that loads comfortably with a 8K context can fail at 128K on the same card.

This matters more for coding than for chat, because agentic coding is the use case that genuinely consumes context. An agent reading a repository, running tests, reading stack traces, and iterating will fill a long window quickly. The practical approach is to decide your working context first - how much of a codebase does the agent actually need resident? - and then size the model to leave room for it, rather than choosing the largest model that technically loads and discovering the context budget is gone.

On the serving side, if you are running a model for more than one user or more than one session, concurrency multiplies the problem. Long-context requests from multiple clients against a 27B model can double the footprint. If you are deploying at 256K context, chunked prefill and batched-token limits are the settings that keep memory stable during large prefills rather than letting it spike.

#9. Licensing: What You Can Actually Ship

Two of these three models carry permissive licenses with no user caps and no commercial restrictions. That is a bigger deal than it sounds.

Qwen3.8-27B ships under Apache 2.0. Gemma 4 ships under Apache 2.0. Kimi K2.7 Code ships under a Modified MIT license. All three allow self-hosting and commercial use, which removes the category of legal friction that made earlier open-weight generations awkward for anything beyond experimentation - the monthly active user caps, the field-of-use restrictions, the acceptable use clauses that required a lawyer to interpret.

If you are building a product on top of a local model, the license is a strategic input rather than a formality. Apache 2.0 weights mean you can ship, fine-tune, and distribute derived models without a licensing conversation. A Modified MIT license is permissive but the word 'modified' is doing work, so read the actual terms rather than pattern-matching on the name. And regardless of license, if you fine-tune and redistribute, keep provenance records of the base checkpoint and its version, because these models are revised more often than people expect.

#10. Behaviour Inside an Agent Loop

Single-prompt quality and agent-loop reliability are different properties, and the second one is what you will actually feel.

An agent asks a model to do something specific: read a file, decide what to change, call a tool, read the result, and adjust. Failure modes there are not usually about knowledge. They are about instruction-following drift over many turns, tool-call formatting that degrades as context fills, and the model losing track of what it already tried. This is why Terminal-Bench and SWE-bench style evaluations are more informative for this use case than knowledge benchmarks, and why Qwen's decision to foreground agentic evaluations in its launch card was a reasonable reflection of what the model was trained for.

Practical implications differ by model. Qwen3.8-27B has thinking on by default with adjustable reasoning_effort, and whether prior reasoning blocks are preserved across turns is a setting you control - which directly affects how much context the agent burns per step. Kimi K2.7 Code cannot have thinking disabled at all, which is a design commitment to reliability at the cost of flexibility. Gemma 4 supports function calling across the family, but if you are running the E2B or E4B sizes, expect to keep the task scope tight; small models handle narrow, well-specified steps far better than open-ended planning.

One more thing that matters and is rarely mentioned: quantization affects agent behaviour more than it affects chat quality. A model that still writes fluent prose at aggressive quantization may have lost enough precision to start producing malformed tool calls. If your agent suddenly develops a habit of emitting broken JSON, test a less aggressive quantization before blaming the harness.

#11. Quantization: Where the Quality Actually Goes

Quantization is the lever that makes all of this possible, and it is also the one most often pulled too hard.

Going from BF16 to 4-bit takes Qwen3.8-27B from roughly 55.6GB to around 18GB. That is not a small optimisation; it is the difference between a server and a desktop. The cost is precision, and precision does not degrade uniformly across capabilities. Conversational fluency survives aggressive quantization well. Arithmetic, long-chain reasoning, strict format adherence, and tool-call correctness degrade earlier and more visibly.

A reasonable default is Q4_K_M, which is where the 0.6GB-per-billion estimate comes from and which most people find to be the best quality-per-gigabyte trade. If you have headroom, moving up to a higher-precision quantization is usually a better use of memory than moving up a model size, particularly for agentic work. If you are short on memory, dropping to 3-bit to force a larger model onto the card is usually a mistake: a well-quantized smaller model beats a badly-quantized larger one for anything requiring precision.

Also check who produced the quantization. Different GGUF builds of the same model are not equivalent, and dynamic quantization approaches that preserve precision selectively in the layers that need it most have become a meaningful differentiator. It is worth trying more than one build of the same model before concluding the model itself is disappointing.

#12. A Practical Evaluation Protocol

Benchmarks tell you about someone else's tasks. Half a day of structured testing on your own repository tells you about yours.

Pick five to ten tasks from your actual work that you have already solved, so you know what a correct answer looks like. A bug fix with a known root cause. A refactor across three or four files. A test that needs writing for existing code. A stack trace that needs diagnosing. Something that requires reading documentation you have locally. These should be representative of what you actually do, not showcase tasks.

Then run each candidate model through all of them under identical conditions: same agent harness, same context settings, same quantization tier where comparable. Record three things per task - whether the output was correct, how many turns it took, and how long it took in wall-clock time. The turn count is the most underrated metric, because a model that gets there in twelve turns costs you more context, more time, and more chances to go wrong than one that gets there in four.

  • Use tasks you have already solved, so correctness is unambiguous.
  • Hold the harness, context settings, and quantization constant across candidates.
  • Record correctness, turn count, and wall-clock time separately.
  • Test at the context length you will actually use, not a convenient short one.
  • Re-test when you change quantization build, not just when you change model.

Budget half a day for this. It is the single highest-return activity in the entire local-model decision, and it replaces an unbounded amount of forum argument with an answer that is actually about your work.

#13. Common Mistakes

  • Choosing by leaderboard position before checking whether the model fits your memory budget.
  • Reading MoE active-parameter counts as memory requirements - Kimi K2.7 activates 32B but stores 1T.
  • Forgetting the KV cache and then being surprised when a long-context session spills to system RAM.
  • Comparing vendor benchmark numbers across different harnesses as if they were the same experiment.
  • Quantizing too aggressively to fit a larger model, then blaming the model for malformed tool calls.
  • Running weights pulled months ago - several of these checkpoints have been revised since release.
  • Treating a coding-specialist model as a general assistant, or a general model as a coding specialist.
  • Testing with single prompts when your actual use case is a multi-turn agent loop.

#14. The Verdict

Three models, three clearly different answers, and the deciding variable is hardware rather than capability.

Qwen3.8-27B is the recommendation for anyone with 24GB of VRAM or unified memory who wants agentic coding from a local model. It was trained for exactly that, its generational gains cluster in exactly that area, and roughly 18GB of quantized weights leaves room for a workable context. The vendor benchmarks should be read as positioning rather than proof, but the direction they point is consistent with how the model behaves in practice.

Gemma 4 is the recommendation for anyone below that tier, anyone who needs multimodality, and anyone who wants one family covering multiple devices. The 12B Unified at around 7.6GB is the most useful single model for an 8GB card in 2026, the 26B A4B is the speed-conscious choice on a 24GB card, and the MTP drafters are a free latency win most people never enable.

Kimi K2.7 Code is the recommendation for almost nobody as a local model, and a serious option as an API with an open-weight escape hatch. Its value to a local-first developer is optionality rather than deployment - the knowledge that the weights exist under a permissive license, that self-hosting is possible if the economics ever justify eight GPUs, and that the vendor knows it.

The broader point is that the open-weight ecosystem has split into two tiers that do not compete with each other. One tier runs on hardware you already own and is improving fast enough that the gap to frontier closed models keeps narrowing for practical coding work. The other tier is open in license and closed in practice, gated by hardware rather than by terms. Knowing which tier you are shopping in is most of the decision.

(Frequently asked questions)

Can I run Kimi K2.7 Code on a consumer GPU?

No. It is a mixture-of-experts model with one trillion total parameters and 32 billion active per token. The active count reduces compute per token, not the memory needed to store the weights. A representative self-hosting configuration uses tensor parallelism across eight GPUs. For consumer hardware the realistic path is the API, with the open weights serving as an escape hatch rather than a deployment plan.

What is the best local coding model for a 24GB GPU?

Qwen3.8-27B is the strongest current option. Its Ollama packages are around 18GB, which leaves real headroom for context on a 24GB card, and its training focus is agentic software engineering rather than single-response quality. Gemma 4 31B is the alternative if you want a stronger general model, and Gemma 4 26B A4B is worth testing for faster generation at similar quality.

How much VRAM do I need per billion parameters?

Roughly 0.6GB per billion parameters at Q4_K_M quantization, plus 20 to 30 percent headroom for KV cache and context. That puts 7 to 12B models on 8GB cards, the 14 to 20B class on 16GB, and 27 to 31B models on 24GB. These are planning estimates derived from parameter counts, so verify the actual package size before pulling.

Does a mixture-of-experts model use less memory?

No. MoE routing reduces the compute used per token by activating only a subset of experts, but all of the weights still have to be resident. This is the most common misunderstanding in local model planning, because MoE marketing emphasises the active parameter count rather than the total.

Are the benchmark numbers in model cards trustworthy?

They are evidence with a known bias. Nearly all of these figures are vendor-run, often on different harnesses with different temperatures, context windows, and timeouts. Some benchmarks are designed in-house by the same vendor. Treat the ordering as probably right and the margins as probably wrong, and attribute every number to whoever ran it.

Which model is best if I only have 8GB of VRAM?

Gemma 4 12B Unified at roughly 7.6GB is the strongest general-purpose option at that tier and brings image and audio input with it. If you want something dedicated to code, JetBrains' Mellum2-12B is the strongest coding-specific pull that fits. Do not force a 27B model onto an 8GB card by over-quantizing.

Does quantization hurt coding performance?

Yes, and unevenly. Conversational fluency survives aggressive quantization well, but strict format adherence, long-chain reasoning, and tool-call correctness degrade earlier. If an agent starts producing malformed tool calls, test a less aggressive quantization before blaming the harness. Q4_K_M is a reasonable default for most hardware.

Is Gemma 4 good enough for serious coding work?

It is a strong general model with solid coding ability rather than a coding specialist. The 31B reports around 80 percent on LiveCodeBench and a Codeforces Elo near 2150. For heavily agentic software engineering, Qwen3.8-27B's training focus shows. For mixed workloads involving documents, images, audio, or many languages, Gemma 4 is the better all-round fit.

Do long context windows cost memory?

Yes. The advertised context window is a capability, not a free one. The KV cache grows with the context you actually use and comes from the same memory pool as the weights, and concurrency multiplies it. Decide your working context first, then size the model to leave room for it.

How should I actually choose between these models?

Work out your memory budget, eliminate everything that cannot fit with context headroom, then test the survivors on five to ten tasks from your own repository that you have already solved. Hold the harness and quantization constant, and record correctness, turn count, and wall-clock time. Half a day of this beats any amount of benchmark reading.
